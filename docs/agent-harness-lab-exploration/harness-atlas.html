Rung 4 mechanism — fallible LLM → safe decision (left → right)
① Propose
LLM reads convo+flows+slots → emits a command from a fixed grammar. Menu, not free-writing.
② Validate
Code: is this transition legal from current node given preconditions/slots? Illegal → reject.
③ Confidence
Low/ambiguous → don't jump. Emit Clarify, safe default, or human.
④ Reversibility tier
FAQ → trust. Refund/account → deterministic preconditions or human approval.
⑤ Execute / Repair
Legal+confident → run. Digression → push stack, handle, pop, resume.

LLM = linguistic intelligence (intent, certainty, digression). Code = business logic + legal move-set. Command grammar + stack = the contract. That's the whole CALM design and the upgrade path for your AI-gambit jump.

Atlas › 4 · Rung 4 Deep-Dive

Rung 4, implemented — grammar, proposal, confidence, failures

How "LLM proposes / code validates" is actually built for a gambit graph.

① A starter command grammar for your gambit system (LLM may ONLY emit these)
GoToGambit(id) propose a jump; rejected if not a legal edge · Stay() keep talking · SetVar(k,v) record input
Clarify(q) "I'm not sure" → ask user · Digress(id) push side gambit · Resume() pop back
Cancel() abandon flow · Escalate(reason) human handoff · CannotHandle() escape hatch (grammar gap)
② Three ways to implement "Propose"
a. Structured JSON output — {cmd,args,confidence} vs schema. Simplest; confidence self-reported.

b. Tool-call with enum — GoToGambit arg = enum of only legal next gambits. Hardest to emit invalid. Best default.

c. Fine-tuned small model — CALM's path (~Llama-8B). Cheap/fast/consistent; needs data. Do once volume justifies.
③ Where confidence comes from
Self-reported field — easy, over-confident. Weak floor alone.

A Clarify command — CALM's trick: make "unsure" a valid move. Strongest, cheapest.

Logprobs — real signal, more plumbing.

Double-sample disagree — 2× cost.
④ Where rung 4 STILL fails — and the defense
FailureDefense
Legal-but-wrong jump (passes validation — it IS a legal edge)Richer edge preconditions · reversibility tiering · supervisor model · post-hoc verification before side-effects
Confidently wrong (high self-confidence, wrong cmd)Never trust self-confidence as floor; deterministic preconditions are the floor; consequential edges always gated
Grammar gap (user wants what no command expresses)Always include CannotHandle/Escalate; review logs to grow the grammar
Stack pathologies (infinite digression, user never returns)Stack depth limit · TTL on suspended gambits · "unfinished X — continue?" resume prompt
Multi-command sequence ordering/atomicityValidate the whole sequence transactionally; all-or-nothing

Two different questions need two different stores. Your system has one and is missing the other.

Typed slots answer “what do we know?”. The stack answers “where are we and how do we get back?” You need both. You have the first; the stack is the missing piece that makes digression+resume possible.

Anatomy of a stack frame
A frame = { gambitId, localVars, stepCursor (which step within the gambit), returnTo }. The stack is a LIFO list of frames; the top frame is active. Persisted per conversation (not in memory).

Flat-state system: no frame to pop back to → resuming means re-running CollectAddress from the top (losing collected fields) or just breaking. The stepCursor is what makes resume exact.
E × F — the stack must survive across turns
Customer answers, closes browser, returns tomorrow. So the stack is durable persisted state, loaded on every inbound message.

Suspend (collect-input) = persist stack+slots, return.
Resume (inbound msg) = load stack; top frame's stepCursor says exactly where to continue.

Mental model: Temporal Signal / Restate awakeable / LangGraph interrupt+checkpoint. Convex is already your durability substrate — the stack is just a persisted doc per conversation; no Temporal needed.

Pitfall: if resume re-runs the frame body, side-effects must sit after the suspend point or be idempotent. stepCursor is what lets you skip already-done steps.
Stack op per command (B × E wiring)
GoToGambit → replace top frame (normal transition, no return)

Digress → push a frame (expects return)

flow-complete / Resume → pop, continue parent at its stepCursor

Cancel → pop + discard frame & its local vars

Escalate → snapshot full stack → handoff payload

Key: "transition" (replace) vs "digression" (push) is a real semantic split — your grammar already separates them, so the stack just honors it.
Stack pathologies & guards
PathologyGuard
Unbounded depth (digression in digression in digression)Max stack depth (e.g. 5) → beyond it, flatten or escalate
Orphaned/stale frame (digressed, never returned)Per-frame TTL → on resume if stale: "you had an unfinished change-of-address — resume or discard?"
Resume ambiguity (>1 suspended user-facing frame)LIFO default, but prompt the user when more than one is pending
Pop into a changed world (order shipped while suspended)Re-validate frame preconditions on resume, not only on entry
State bloat over a long conversationCompact history (summarize old turns); never compact stack or typed slots — they're source of truth
Cross-frame variable leakageTwo tiers: session-global typed slots + frame-local scratch vars

What to build on your stack: keep your typed pre/post vars (the ✅ "what we know" tier) → add a persisted dialogue-stack doc per conversation in Convex (array of frames) → wire the rung-4 grammar to stack ops above → on collect-input persist stack+slots, resume from top frame's stepCursor → add the six guards → compact transcript only, never stack/slots.

Your model treats "add intelligence" = jump to the gold cell. But the violet cell is a lighter, safer intelligence injection — and it's exactly what fixes the digression problem from Dimension E without going generative.
Recommendation — three tiers inside ONE workflow (granularity is per-gambit, not global)
Tier A · Pure deterministic gambit
templated msg, code routing. Your existing 500-gambit flows. Unchanged.
Tier B · Deterministic + understanding overlay
SAME templated gambit, but a CALM-style turn-understanding watcher runs every turn → detects digression/correction/cancel/escalate → manipulates the stack. Makes your whole backbone off-script-robust without making it generative.
Tier C · AI-agent gambit
full per-node generative agent for genuinely open segments. Heavier G+H. Use where open conversation is the point.
Whole-flow agent (level 3 / ★2) = the degenerate case: a workflow that is one Tier-C gambit with everything as tools. It's not a separate thing — it's a coordinate.
Why C drives your G & H burden (dimensions interact)
The more the LLM generates user-facing words, the more you don't know what the bot will say → the heavier your guardrail (G) and verification (H) must be. Tier A: ~none. Tier B: light (LLM only picks authored content, can't invent words — the safety win). Tier C: heavy (output validation, grounding checks, policy gates, supervisor). "Authored words" is itself a guardrail — Tier B gets robustness for free that Tier C must pay for.

For your system: don't treat the AI-agent gambit as the only intelligence. Add Tier B (turn-understanding overlay + stack from Dimension E) to your existing deterministic gambits → your 500-gambit workflows become digression-robust and stay fully controllable. Reserve Tier C (generative AI-gambit) for the few segments where open-ended conversation is the actual goal, and accept it needs the heavier G/H.

F deep-dive — cross-turn suspension
Your collect-input is inherently a suspension point. Three models:

a. Durable signal / awaitable ★1 — suspend, persist state, an inbound message resumes. Survives the user closing the browser for a day. (Temporal Signal / Restate awakeable / Convex — you have this free.)

b. Re-entrant replay — resume re-runs the node from the top → side-effects must be after the suspend point or idempotent (the LangGraph pitfall, restated).

c. Synchronous-only — no real cross-turn; breaks for CX the moment the user pauses.

Takeaway: F and E are one mechanism — the durable stack snapshot IS the suspension checkpoint.
G deep-dive — guardrail enforcement
Core principle: probabilistic compliance vs deterministic constraint. "Follow policy" in a prompt is probabilistic; a code gate that blocks is deterministic. Two kinds (Fowler's guides vs sensors):

Feedforward — constrain what the agent CAN do: allowed-tools, enum jumps, path constraints (= the rung-4 validate stage IS a feedforward guardrail).

Feedback — check what it DID: output validators, grounding checks (= overlaps H).

Layered (★2 / high-stakes): code rules → supervisor model → adversarial tests. G scales with C: the more generative the gambit, the heavier G.
The synthesis that simplifies everything
The 8 dimensions are not 8 independent decisions. Three are the design (B control-locus · C granularity · E state/stack); five mostly follow: A = the graph you already have (needs E's stack) · D = single for the live loop · F = how E persists · G = the rung-4 validate gate (B) scaled by C · H = the pre-side-effect gate from B-stage④. Get B, C, E right and the rest fall into place. That is the whole framework in one sentence.
